# legirss

Windows 用の RSS リーダー。Kotlin Multiplatform と Compose Multiplatform で書いている。
ターゲットは jvm（デスクトップ）だけ。利用者は 1 人で、タスクトレイに常駐させて使う。

小さな文字と詰めた行で 1 画面に多くの記事を並べるため、**Material は使わない**。
画面の部品は `compose.foundation` と `compose.ui` だけで自作している。

## モジュール

- `shared/` … ロジックと画面の本体。大半を `commonMain` に置き、JVM に頼るものだけ `jvmMain` に置く
- `desktopApp/` … Windows のエントリポイント。ウィンドウ、タスクトレイ、自己更新、OS とのやり取り

パッケージは `to.sava.legirss`。

| 場所 | 中身 |
|---|---|
| `shared` `data/` | `LegirssStore`（データベースへの窓口）、`Schema.sq`（SQLDelight）、`DatabaseBackup` |
| `shared` `feed/` | フィードの取得（`FeedFetcher`）、解釈（`FeedParser`）、文字コード（`FeedText`）、フィードの発見（`FeedLocator`） |
| `shared` `update/FeedUpdater` | チャンネルの更新。並行して取得し、取り込みと古い記事の整理を行う |
| `shared` `html/` | 記事の HTML を描画用のブロックに変える |
| `shared` `opml/` | OPML の読み書き |
| `shared` `ui/` | `MainViewModel`（状態と操作）、`MainState`、`MainActions`（操作とキー割り当て）、`MainScreen`、`Dialogs` |
| `shared` `ui/component/` | 自作の部品。`TreeView` `DataTable` `SplitLayout` `PopupMenu` `ModalDialog` `HtmlContent` |
| `desktopApp` | `Main.kt`（組み立て）、`TrayController`、`SingleInstance`、`StartupRegistration`、`BrowserLauncher`、`AppLog` |
| `desktopApp` `update/` | アプリの自己更新。マニフェストの署名の確認、配布物の取得と照合、入れ替えのスクリプト |

`update` という名前のパッケージが 2 つある。`shared` のものはフィードの更新、`desktopApp` のものは
アプリ自身の更新で、別の機能。

## 守っている動作

変えるときは、利用者に確かめてからにする。読む流れを支えている決まりで、うっかり崩しやすい。

- **読んでいる途中で一覧の行を動かさない。** 記事の状態を変えても並べ直さない。並べ直すのは、
  ツリーでノードを選んだとき、ウィンドウを出したとき、手動で更新したとき、F5 を押したときだけ。
  ウィンドウを出している間の定期更新は、ツリーの件数だけを更新する
- **記事を選んで表示すると既読になる。** Shift や Ctrl で印を付けただけの記事は既読にしない
- **Space は、一覧で一番下にある未読へ移る。** 日時ではなく一覧での位置で決める。同じ日時の記事が
  並ぶフィードがあるため
- **ツリーをクリックしたあとのフォーカスは一覧に置く。** クリックに続けてキーで読み始められるように
  するため。ツリーをキーで操作するのは、F6 でフォーカスを移したときだけ
- **未読の記事と保護した記事は、整理で消さない。** 消すのは、残す数と日数を超えた既読だけ
- **整理や削除で消した記事は、フィードに残っていても登録し直さない。** 識別子を `seen` テーブルに
  控えている
- **データベースへの操作は 1 つずつ順に実行する。** ドライバがスレッドごとに別の接続を使うため、
  並行して書き込むと失敗する。`LegirssStore` の `access` を必ず通す
- **1 つの失敗でアプリを止めない。** チャンネルごとの更新の失敗は記録して次へ進む。
  画面の操作から起きた失敗は、記録してステータスバーに出す

## データ

- 置き場所は `%APPDATA%\legirss`。開発用の起動（`:desktopApp:run`）だけは
  `desktopApp/build/dev-data` を使い、利用者のデータに触れない
- スキーマは `Schema.sq` に書く。問い合わせの追加や変更は自由にできる。
  **テーブルの定義を変えるときは、下の「スキーマを変える」の手順で移行のファイルを足す。**
  足さないと、既にあるデータベースが古い定義のまま開かれて、問い合わせが失敗する
- 設定は `setting` テーブルに、名前と値の組で持つ。値と文字の対応は、持ち主のクラス
  （`AppSettings` `ScreenLayout` `WindowBounds`）の `toSettings` と `fromSettings` に置く

### スキーマを変える

データベースのファイルには、スキーマの版が記録されている（`PRAGMA user_version`）。アプリが持つ版より
古ければ、開くときに SQLDelight が移行のファイルを順に実行する。版は、移行のファイルの数に 1 を足した値になる。

1. `Schema.sq` のテーブルの定義を、変えたあとの形に書き換える
2. いまの版の番号を名前にした移行のファイルを、`Schema.sq` と同じ場所に足す。版 1 から 2 へ上げるなら
   `1.sqm`。中には、古い定義を新しい定義に変える文（`ALTER TABLE` など）を書く
3. 新しい版のスキーマの控えを作って、コミットに含める

   ```
   ./gradlew :shared:generateCommonMainLegirssDatabaseSchema
   ```

   `shared/src/commonMain/sqldelight/databases/` に `2.db` のような名前でできる
4. `./gradlew check` を通す。移行のファイルを順に実行した結果が `Schema.sq` と同じ形になることを、
   `verifyCommonMainLegirssDatabaseMigration` が確かめる

移行の前には、元の状態の複製が `backup\legirss-before-migration-v版.db` に自動で残る。
日ごとのバックアップとは別のもので、古くなっても消さない。

公開した移行のファイルは書き換えない。利用者のデータベースには実行した結果が残っているので、
直すときは次の版の移行のファイルを足す。

## ハマりどころ

実際につまずいたもの。同じところを触るときに読む。

- **Ksoup の `Element` に、同じ名前の拡張関数を足さない。** `attribute(name)` などのメンバーがあり、
  拡張関数は負けて、型の合わないコンパイルエラーになる。別の名前（`attributeText` など）を付ける
- **`BoxWithConstraints` の外から、中の部品の `FocusRequester` を呼ばない。** 中身は配置の段階で
  組み込まれるので、外側の `LaunchedEffect` から `requestFocus()` を呼ぶと、まだ結び付いておらず失敗する。
  フォーカスを移す処理は、対象の部品と同じ composable の中に置く
- **`clickable` は、クリックされるとフォーカスを取る。** 押したあとも別の部品にフォーカスを残したい
  ときは、クリックの処理の中で明示的に戻す（ツリーをクリックしたあと、一覧へ戻しているのがこれ）
- **文字の入力欄は、Space などの KeyDown を消費しない。** 入力欄で打ったキーがウィンドウ全体のキー
  処理まで届く。ダイアログを出している間は、ウィンドウ側のキー処理を止める（`Main.kt` の `onKeyEvent`）
- **データベースの並行書き込みの問題は、メモリ上のデータベースのテストでは出ない。** ドライバは
  ファイルのデータベースのときだけ、スレッドごとに別の接続を使う。並行の動作を確かめるテストは、
  ファイルのデータベースで書く
- **`java.util.logging.FileHandler` のファイル名には `%g` を入れる。** 世代を残す設定にすると、
  `%g` が無い名前には末尾に `.0` が足されて、拡張子が変わる
- **GUI のアプリでは標準エラーが誰にも見えない。** 失敗は `AppLog` で記録する
- **ウィンドウを出さない描画では、実機との差が残る。** 利用者の画面は高解像度で、文字の上下の位置の
  ような細かい差は等倍の描画に出ない。見た目の細部は、最後に利用者の画面で確かめてもらう

## 検証

コミットの前に必ず通す。

```
./gradlew check
```

- **パイプは gradle の失敗を隠す。** `| tail` や `| grep` を通すと、パイプの最後のコマンドの終了
  コードを見てしまう。出力をファイルへ落として、終了コードを直接見る
- **画面は、ウィンドウを出さずに描いて確かめられる。** `MainScreenRenderTest` が、画面を PNG にして
  `shared/build/preview/` に出す。配置や見た目を変えたら、ここへ状態を足して画像を見る。
  マウスやキーの操作、フォーカスの移り方、ポップアップの位置は、この方法では確かめられない
- **アプリを起動して確かめるときは、利用者に断ってからにする。** 利用者の画面を使うため。
  進め方と、終了のあとに見るものは verify-on-device skill を参照
- データベースの状態は `tools/inspect_db.py` で見られる。読み取り専用で開くので、アプリが動いていても使える
- テストには、何を検証しているかを KDoc で書く
- テストが作る一時ファイルは、ビルドディレクトリの下に置かれる

## 版を上げる

`vMAJOR.MINOR.PATCH` のタグを push したときだけ配布物が出る。main への push では出ない。
手順と注意点は release skill を参照。

タスクトレイのメニューにある「Windows の起動時に開始する」と自己更新は、インストールしたアプリから
起動したときだけ働く。開発用の起動では、どちらも無効になる。

アプリのアイコン（`desktopApp/icons/legirss.ico`）は、タスクトレイのアイコンと同じ絵から作っている。
絵（`TrayController.drawIcon`）を変えたら、`./gradlew :desktopApp:generateIcon` で作り直してコミットする。

## 書き方

- 画面の文字、コメント、コミットの件名は日本語で書く
- 用語は一般的な言い方を使う。ダイアログ、マニフェスト、通知、メッセージなど。
  和語への言い換えに寄せすぎない
- コメントに作業の経緯を書かない。結果としての仕様だけを書く
  （「○○せず△△する」ではなく「△△する」）
- 「今は〜」「後で〜」のような暫定的・時間的な記述を残さない。後続変更が確実な箇所だけ、
  具体的な条件を明記した TODO として書く
- その場かぎりの用語（会話中の造語、開発中のマイルストーン識別子など）を持ち込まない
- 文字、寸法、キーなどの値は、名前を付けた定数にする

## コミット

- 件名は命令形で簡潔に。1 コミット 1 論理変更にまとめる
- 生成ツールのフッタ（`Co-Authored-By` 等）は付けない
