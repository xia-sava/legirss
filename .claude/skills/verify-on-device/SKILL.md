# 実機で確かめる

テストと、ウィンドウを出さない描画（`MainScreenRenderTest`）で確かめられるのは、処理の結果と画面の配置まで。
マウスやキーの操作、フォーカスの移り方、ポップアップやダイアログの出方、日本語の入力、OS とのやり取りは、
利用者の画面で動かさないと分からない。

利用者の画面を借りる作業なので、進め方に決まりがある。

## 起動の前

1. **テストを通しておく。** `./gradlew check`
2. **起動してよいかを利用者に聞く。** 以前に許可をもらっていても、その都度聞く。
   利用者はほかの作業と並行していることが多い
3. **見てほしい点を、優先度の高い順に伝える。** 変更した箇所と、巻き添えで変わりうる箇所を挙げる。
   いつもの読む流れ（ツリーをクリック → Space → ↑）が変わっていないかは、画面を触る変更なら毎回入れる

## 起動する

開発用の起動は、裏で走らせる。終了すると通知が来るので、待つ間はほかの作業をしない。

```
./gradlew :desktopApp:run
```

- データは `desktopApp/build/dev-data` に置かれ、利用者のデータ（`%APPDATA%\legirss`）には触れない
- 終了は、タスクトレイのメニューの「終了」から行ってもらう。ウィンドウを閉じただけでは終わらない
- インストール済みの legirss が動いていても、データの場所が違うので同時に動かせる。
  タスクトレイにアイコンが 2 つ並ぶことは、先に伝えておく

開発用の起動では、次の 2 つが働かない。確かめるには、インストーラを作って入れてもらう
（release skill の「配布せずに手元で試したいとき」）。

- タスクトレイのメニューの「Windows の起動時に開始する」
- アプリの自己更新

## 終了のあと

**終わったことを、まず単独で伝える。** 結果の説明は、そのあとに別に行う。
画面を借りている間は、いつ終わるかが見えないことが利用者の負担になる。

そのうえで、次の 3 つを見る。

1. **起動の出力。** 例外が出ていないかを見る。次の警告は害が無いので、報告しなくてよい
   - `WARNING: A restricted method in java.lang.System has been called`（JDK 25 のネイティブ読み込み）
   - `SLF4J` で始まる行

2. **記録用のファイル。** 失敗はここに残る。空なら失敗は無い

   | 動かし方 | 場所 |
   |---|---|
   | 開発用の起動 | `desktopApp/build/dev-data/legirss.0.log` |
   | インストールしたもの | `%APPDATA%\legirss\legirss.0.log`、更新のあとは `update-apply.log` も |

3. **データベースの状態。** 読み取り専用で開くので、アプリが動いていても使える

   ```
   python tools/inspect_db.py desktopApp/build/dev-data/legirss.db
   ```

   スキーマの版、チャンネルと記事の数、失敗しているチャンネル、設定が出る。
   操作の前後で数が合うか、設定が保存されたかを、ここで確かめる

## 報告する

- 確かめられたことと、確かめられなかったことを分けて書く。利用者が見ていない点を、確かめたことにしない
- データが減った、増えたなどの変化は、数を添えて書く。想定どおりの変化でも黙らない
- 利用者の感想を聞く。見てほしい点として挙げたものを、そのまま問いにする

## 気をつけること

- **利用者のデータベース（`%APPDATA%\legirss\legirss.db`）には書き込まない。** 読むのは構わない。
  書く必要が出たら、アプリを終了してもらい、コマンドを見せて確認を取ってから行う
- **開発用のデータは、ビルドディレクトリの下にある。** `./gradlew clean` で消える
- **古い記事の整理は、更新のたびに働く。** 開発用のデータで更新が走ると、残す範囲を外れた既読が消える。
  記事の数が減ること自体は不具合ではない
